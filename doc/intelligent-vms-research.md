# 지능형 VMS: 기술 조사 및 의견

작성일: 2026‑09‑06 · 상태: 초안(v0.1) · 관련 문서: [intelligent-vms-concept.md](intelligent-vms-concept.md)

이 문서의 수치 중 **"추정"**이라고 표시한 것은 공개 자료와 경험칙에 기반한 계산이며, 실제 하드웨어에서 측정해 바꿔야 한다. 측정 방법은 13절에 있다.

## 1. 요약 (결론 먼저)

1. **개념은 실현 가능하다.** 로컬 VLM + JSON 스키마 강제 출력 + 하이브리드 검색 조합은 2026년 현재 소비자용 GPU 한 장으로 16채널 규모를 감당한다. 상용 VMS(AxxonSoft 등)도 같은 방식의 "VLM 메타데이터 검색"을 이미 제품화했다.
2. **병목은 VLM 추론 시간이다.** 16채널을 전수 분석하면 캡처 간격의 하한이 `16 × (이미지당 추론 시간)`이다. 4B급 모델로 2~3초/장이면 간격 30~50초가 현실적이다. 10초 간격을 원하면 변화 감지 게이팅이나 GPU 증설이 필요하다.
3. **엔진 후보는 Gemma 4를 1순위로 두되, 인터페이스로 분리해 나중에 결정한다.** Gemma 4는 전 사이즈가 이미지 입력을 지원하고 Apache 2.0이라 상용화 부담이 적다. Gemma 3는 별도 이용약관(Gemma Terms)이다.
4. **검색은 "구조화 필터 + 키워드 + 벡터"를 결합해야 한다.** 벡터만 쓰면 "노란색"과 "주황색"을 구분 못 하고, 필터만 쓰면 서술형 질의를 못 다룬다.
5. **가장 큰 선행 작업은 AI가 아니라 녹화다.** 현재 코드에 녹화와 타임스탬프 재생이 없다. "클릭하면 재생"은 이것 없이는 성립하지 않는다.
6. **Analyzer는 별도 Python 서비스로 시작하는 것을 권한다.** 엔진 교체, 원격 배치, 실험 속도 모두에서 C++ in‑process보다 유리하다. 계약(HTTP API)만 고정한다.

## 2. VLM 엔진 선택지

### 2.1 모델 비교

| 모델 | 크기 | 이미지 입력 | 비디오 입력 | 라이선스 | VRAM (Q4 기준, 추정) | 비고 |
|------|------|-------------|-------------|----------|----------------------|------|
| **Gemma 4 E2B / E4B** | 2B / 4B (effective) | ○ | ○ | Apache 2.0 | 4~6 GB | 엣지용. 오디오 입력도 지원. 16GB 카드에서 가장 여유 |
| **Gemma 4 12B** | 12B | ○ | ○ | Apache 2.0 | ~10 GB (공식: 16GB VRAM 권장) | 인코더 없는 통합 구조. 품질/속도 균형점 후보 |
| **Gemma 4 26B MoE** | 26B (활성 파라미터 적음) | ○ | ○ | Apache 2.0 | 16~20 GB | 품질 상위. 24GB 카드 필요 |
| Gemma 4 31B Dense | 31B | ○ | ○ | Apache 2.0 | 20~24 GB | 워크스테이션급 |
| Gemma 3 4B / 12B / 27B | 4B / 12B / 27B | ○ (896×896 → 256 토큰) | × | Gemma Terms of Use | 4 / 9 / 17 GB | 검증된 선택. 상용 배포 시 약관 확인 필요 |
| Qwen2.5‑VL / Qwen3‑VL | 3B~72B | ○ | ○ | Apache 2.0 (일부 크기) | 다양 | 세밀한 속성·OCR 강점. 한국어 양호 |
| Llama 3.2 Vision | 11B / 90B | ○ | × | Llama License | 8 / 55 GB | Ollama 지원. 한국어는 약한 편 |
| LLaVA 계열 | 7B~34B | ○ | × | 다양 | 5~20 GB | 레거시. 구조화 출력 안정성 낮음 |

의견: **1차 실험은 Gemma 4 12B(16GB 카드) 또는 E4B(12GB 이하 카드)로 시작**한다. 같은 프롬프트로 Gemma 3 12B, Qwen 계열을 병렬 평가해 속성 정확도와 속도를 비교하고 결정한다. 어느 쪽이든 Ollama에서 `format`(JSON 스키마) 파라미터로 출력을 강제할 수 있으므로 코드 변경 없이 모델명만 바꾸면 된다.

### 2.2 이미지 토큰 비용

Gemma 3는 896×896 입력을 SigLIP 인코더로 처리해 이미지 1장을 **256 토큰**으로 고정 압축한다. 종횡비가 다른 입력은 Pan & Scan으로 타일링되어 토큰이 늘어난다. 실무 함의:

- 캡처 이미지를 **정사각형에 가깝게, 896px 이하로** 미리 리사이즈해서 보내면 Pan & Scan 오버헤드를 피한다. 16:9 프레임은 레터박스 패딩 또는 중앙 크롭 중 선택(관심 영역이 가장자리에 있으면 패딩).
- 프롬프트(약 300~500 토큰) + 이미지(256) + 출력(100~250)이 한 요청. prefill은 빠르고 **출력 토큰 수가 지연을 좌우**한다. 스키마를 빡빡하게 만들어 출력을 100~150 토큰으로 줄이는 것이 최고의 최적화다.

Gemma 4는 인코더 없는 통합 구조(단일 행렬곱 임베딩)라 토큰 처리 방식이 다르다. 실측이 필요하다.

## 3. Ollama 연동 상세

### 3.1 분석 요청

```http
POST http://analyzer-host:11434/api/chat
Content-Type: application/json

{
  "model": "gemma4:12b",
  "stream": false,
  "keep_alive": "30m",
  "options": { "temperature": 0, "num_ctx": 4096, "num_predict": 300 },
  "format": { "type": "object", "properties": { "...": "6.1절 스키마" }, "required": ["scene", "objects", "tags"] },
  "messages": [
    { "role": "system", "content": "You are a CCTV frame analyst. Describe only what is visible. Use the enum vocabulary. Never guess identity, face, or license plate text. Respond with JSON matching the schema below:\n<schema json>" },
    { "role": "user", "content": "Channel: parking_lot_east. Time: 2026-09-05 14:32 local. Analyze this frame.", "images": ["<base64 jpeg>"] }
  ]
}
```

주의점(Ollama 문서 기준):

- `format`에 JSON 스키마 객체를 넣으면 출력이 스키마에 맞춰 강제된다. 비전 모델에도 동일하게 적용된다.
- 문서는 `temperature: 0`을 권장하고, **스키마를 프롬프트 본문에도 문자열로 한 번 더 넣으라**고 권한다. 두 가지 다 적용한다.
- `keep_alive`를 길게 잡아 모델이 VRAM에서 내려가지 않게 한다. 첫 로딩은 수십 초 걸린다.
- 동시 요청은 `OLLAMA_NUM_PARALLEL` 환경변수로 제어한다. 기본값에서는 요청이 직렬화되므로 큐가 Analyzer 앞단에 있어야 한다.
- Ollama Cloud는 structured output을 지원하지 않는다. 로컬 전용이다.

### 3.2 임베딩

```http
POST /api/embed
{ "model": "bge-m3", "input": ["A man in a yellow t-shirt walks across a parking lot ...", "..."] }
→ { "embeddings": [[...1024 floats...], ...] }
```

- **bge‑m3**: 100개 이상 언어, 1024차원, 8192 토큰. 한국어 질의로 영어 요약을 찾는 교차 언어 검색에 적합. Ollama 라이브러리에 있다.
- 대안: `qwen3-embedding`(다국어, 크기 다양), `nomic-embed-text`(영어 중심, 작고 빠름).
- 임베딩 대상 텍스트는 `summary + " " + tags.join(" ")`로 고정한다. 캡처당 1개.

### 3.3 질의 해석과 재검증

- `parse_query`는 같은 Ollama의 텍스트 모델(Gemma 4 자체로 충분)에 `format`으로 필터 스키마를 강제해 만든다. 입력에 `now`, 타임존, 채널 이름 목록을 준다. "1일 전", "어제 오후", "지난 주말" 같은 상대 시간을 절대 구간으로 바꾸는 것이 핵심이며, 몇 가지 예시를 프롬프트에 넣으면 안정적이다.
- `verify`는 상위 K장의 썸네일과 질의를 VLM에 보내 `{match, confidence, reason}`을 받는다. K=20이면 20번의 VLM 호출이므로 사용자가 명시적으로 눌렀을 때만 실행한다.

## 4. 처리량 계산 (추정)

### 4.1 기본 식

```
필요 처리량 (img/s) = 채널 수 / 캡처 간격(s)
최소 캡처 간격 (s)  = 채널 수 × 이미지당 추론 시간(s)     (직렬 처리 가정)
```

### 4.2 16채널 기준

| 캡처 간격 | 필요 처리량 | 하루 캡처 수 | 이미지당 허용 추론 시간 |
|-----------|-------------|--------------|-------------------------|
| 10초 | 1.6 img/s | 138,240 | 0.63 s |
| 20초 | 0.8 img/s | 69,120 | 1.25 s |
| 30초 | 0.53 img/s | 46,080 | 1.9 s |
| 60초 | 0.27 img/s | 23,040 | 3.75 s |
| 120초 | 0.13 img/s | 11,520 | 7.5 s |

### 4.3 모델별 이미지당 추론 시간 (추정, 출력 150~200 토큰, Q4)

| 모델 | RTX 4060 Ti 16GB / 5060 Ti | RTX 4070 Ti S / 5070 Ti 16GB | RTX 4090 / 5090 |
|------|----------------------------|-------------------------------|-----------------|
| Gemma 4 E4B / Gemma 3 4B | 2.5~4 s | 1.5~2.5 s | 0.8~1.5 s |
| Gemma 4 12B / Gemma 3 12B | 6~10 s | 4~7 s | 2~3.5 s |
| Gemma 4 26B MoE | 불가(VRAM) | 빠듯 | 3~5 s |

Gemma 4의 Multi‑Token Prediction 드래프터(2026‑05)는 디코드 처리량을 최대 3배까지 올린다고 발표됐다. 적용 시 위 수치의 절반 이하가 될 수 있다. 실측 필요.

### 4.4 결론

- **전수 분석**: 4B급 + 16GB 카드로 30~60초 간격이 현실적. 12B는 60~120초.
- **10초 간격**을 원하면 세 가지 중 하나: (a) 변화 감지 게이팅으로 실제 분석 프레임을 20~30%로 줄인다, (b) GPU를 4090/5090급으로 올리고 4B 모델을 쓴다, (c) Analyzer를 별도 서버 2대로 분산한다.
- **권장 기본값: 30초 간격 + 변화 감지 게이팅 + 4B~12B 모델.** 게이팅으로 절약한 예산을 12B 모델의 품질에 쓰는 편이 4B로 10초마다 비슷한 장면을 반복 분석하는 것보다 검색 품질에 유리하다.

## 5. 저장 용량 계산

### 5.1 메타데이터 (30초 간격, 46,080 캡처/일)

| 항목 | 건당 | 하루 | 90일 |
|------|------|------|------|
| JSON 메타데이터 | ~2 KB | 92 MB | 8.3 GB |
| 썸네일 (320px JPEG) | ~25 KB | 1.15 GB | 104 GB |
| 임베딩 (1024 × float32) | 4 KB | 184 MB | 16.6 GB |
| 임베딩 (int8 양자화) | 1 KB | 46 MB | 4.1 GB |

썸네일이 지배적이다. 240px로 줄이거나 보존 기간을 나누면(썸네일 30일, 메타데이터 90일) 절반 이하로 떨어진다.

### 5.2 녹화 (메인 스트림 remux)

| 채널당 비트레이트 | 16채널 합계 | 하루 | 30일 |
|-------------------|-------------|------|------|
| 2 Mbps (720p) | 4 MB/s | 346 GB | 10.4 TB |
| 4 Mbps (1080p) | 8 MB/s | 691 GB | 20.7 TB |
| 8 Mbps (1080p 고화질) | 16 MB/s | 1.38 TB | 41 TB |

일반적인 16채널 NVR 수준이다. 제품 사양에 "30일 보존 시 약 20TB(4Mbps 기준)"를 명시하고, 장기 보존은 서브 스트림 녹화 옵션으로 제공하는 것을 검토한다.

### 5.3 SQLite 규모

90일 × 46,080 = 약 415만 캡처, 객체 테이블은 그 2~3배. SQLite와 FTS5는 이 규모를 문제없이 다룬다. sqlite‑vec의 vec0는 브루트포스 KNN이므로 **시간 필터로 먼저 후보를 줄인 뒤** KNN을 돌리는 것이 필수다(파티션 키 또는 캡처 rowid 범위 조건). 100만 벡터 브루트포스는 수백 ms 수준이다.

| 권장 | RTX 4070 Ti Super / 5070 Ti 16GB | Gemma 4 12B | 30초+게이팅 | 8~12코어, 32GB | 단일 PC 통합형 |

CPU 부하 근거: 메인 스트림은 remux라 디코드가 없고, 서브 스트림(640×360, 10~15fps) 16개 디코드는 최신 8코어에서 20~30% 수준이다(추정). 캡처 시각 부근 키프레임만 디코드하는 방식으로 더 줄일 수 있다.

## 7. 검색 방식 비교

| 방식 | 장점 | 단점 | 역할 |
|------|------|------|------|
| SQL 구조화 필터 (시간, 채널, enum 속성) | 빠름, 정확, 설명 가능 | 서술형 질의 불가, enum에 없는 개념 불가 | **1차 후보 축소** |
| FTS5 키워드 | 빠름, 동의어 사전 적용 가능 | 언어 의존, 표현 변형에 약함 | 보조 |
| 벡터 유사도 (bge‑m3) | 서술형·교차 언어 대응, 표현 변형에 강함 | 색상·수량 같은 정밀 조건에 약함, 브루트포스 비용 | **서술형 매칭** |
| VLM 재검증 | 가장 정확 | 장당 수 초, 비용 큼 | 상위 K 정밀화 (명시적 실행) |
| 멀티모달 임베딩 (CLIP/SigLIP 계열로 이미지 자체를 임베딩) | 텍스트 설명 없이도 검색 가능 | 속성 정밀도 낮음, 별도 모델 | 2차 검토. VLM 설명이 놓친 것을 보완 |

권장 결합: **RRF(Reciprocal Rank Fusion)**로 SQL 필터를 통과한 집합 안에서 FTS 순위와 벡터 순위를 합친다. 가중치는 질의 해석 결과의 `confidence`에 따라 조정한다(enum 필터가 확실하면 필터 비중↑, 자유 서술이 길면 벡터 비중↑).

이벤트 그룹핑: 같은 채널에서 인접 캡처 간격이 `2 × capture_interval` 이하이고 객체 구성이 같으면 하나의 이벤트로 묶는다. 결과 목록은 이벤트 단위로 보여주고, 대표 썸네일은 점수가 가장 높은 캡처를 쓴다.

## 8. 프롬프트 설계 원칙

1. **스키마를 두 번 준다.** `format` 파라미터와 시스템 프롬프트 본문 양쪽에.
2. **enum을 명시하고 "unknown"을 허용한다.** 허용하지 않으면 모델이 추측한다. 색상 오인(주황↔노랑, 남색↔검정)은 VLM의 대표적 약점이라 `unknown`이 있어야 정밀도가 올라간다.
3. **보이는 것만 쓰게 한다.** "Describe only what is visible. Do not infer intent." 한 줄이 환각을 크게 줄인다.
4. **신원 관련 생성 금지.** 얼굴 묘사, 번호판 텍스트, 이름 추측 금지 문장을 시스템 프롬프트에 고정.
5. **채널 힌트를 준다.** 채널 이름("주차장 동측")과 `location_type`을 넣으면 요약 품질과 일관성이 좋아진다.
6. **야간/IR 프레임은 별도 지시.** 흑백 IR에서 색상은 `unknown`으로 강제한다. `scene.lighting`이 `ir`이면 색상 필터는 검색 시 무시한다.
7. **출력 길이 제한.** `summary`는 2문장 이내, `num_predict` 300. 지연의 대부분이 출력 토큰이다.
8. **프롬프트 버전을 메타데이터에 남긴다.** 변경 시 A/B 평가 후 필요하면 과거 데이터 재처리.

## 9. 캡처 전략

| 전략 | 설명 | 장단점 |
|------|------|--------|
| 고정 주기 | interval마다 최신 프레임 | 단순, 예측 가능. 정적 장면에 낭비 |
| 키프레임 정렬 | interval 근처의 I‑frame만 디코드 | 디코드 비용 최소. 서브 스트림 상시 디코드 불필요 |
| **변화 감지 게이팅** | 직전 캡처와의 차이(다운스케일 후 픽셀 차, 또는 경량 검출기)가 임계 이하면 skip | 분석 예산 60~80% 절감(추정). 정적 채널에서 특히 큼 |
| 검출기 트리거 | YOLO 같은 경량 검출기로 사람/차량이 있을 때만 VLM | 정밀하지만 별도 모델·GPU 시간 필요 |
| 다중 프레임 | 3~5초 간격 3장을 한 번에 보내 행동 판단 | Gemma 4는 비디오/다중 이미지 지원. 행동(걷기/뛰기) 정확도↑, 토큰 3배 |

권장: **고정 주기 + 변화 감지 게이팅**으로 시작하고, 게이팅으로 스킵한 시각에도 "변화 없음" 레코드를 남겨 타임라인 연속성을 유지한다(이전 캡처 참조만 저장). 행동 정확도가 부족하면 2차에 다중 프레임을 적용한다.

## 10. 현재 코드베이스에서 선행되어야 할 작업

[known-issues.md](known-issues.md)의 결함을 먼저 고쳐야 16채널 상시 세션이 안정적으로 돈다. 특히:

- `StreamReceiver::stop()`의 `terminate()`는 반드시 제거하고 `AVIOInterruptCB`로 대체한다. 상시 세션에서 카메라 하나가 멈추면 앱 전체가 멈추는 구조는 허용할 수 없다.
- `open()`이 GUI 스레드에서 블로킹하는 문제는 상시 세션 도입과 함께 자연히 워커로 옮겨진다.
- `Recorder`는 현재 `writePacket(AVPacket*)`을 받는 구조라 remux 방식에 그대로 맞는다. `StreamReceiver`가 디코드 전에 패킷을 `Recorder`로 넘기는 훅만 추가하면 된다. 단, 세그먼트 분할(5분마다 새 파일, 키프레임 경계)과 인덱스 기록은 새로 작성해야 한다.
- `PlaybackController`는 파일 단위 seek이 이미 있으므로, 세그먼트를 찾아 열고 `seek(ts - start_ts)`를 호출하는 계층만 추가한다. 세그먼트 경계를 넘어가는 연속 재생은 다음 세그먼트를 미리 열어 두는 방식으로 처리한다.

## 11. 아키텍처 의견: C++ in‑process vs 별도 서비스

| 항목 | C++ in‑process (Qt Network → Ollama) | 별도 Python 서비스 (FastAPI) |
|------|--------------------------------------|------------------------------|
| 배포 | 실행 파일 하나. 단순 | 서비스 2개. 설치 스크립트 필요 |
| 엔진 교체 | 엔진마다 C++ 클라이언트 작성 | Python 생태계(ollama, openai, vllm, transformers)로 즉시 교체 |
| 원격 배치 | Ollama URL만 바꾸면 되지만 게이팅·전처리는 VMS PC에 남음 | 서비스 자체를 GPU 서버로 옮김. VMS PC는 CPU만 |
| 게이팅/검출기 | OpenCV C++ 추가 링크 | ultralytics 등 pip 한 줄 |
| 실험 속도 | 빌드 필요 | 스크립트 수정 즉시 반영 |
| 장애 격리 | Analyzer 문제가 VMS 프로세스에 영향 | 프로세스 분리. VMS는 큐만 쌓음 |

**권장: 별도 Python 서비스.** 이 프로젝트에는 이미 PyQt5 카메라 도구(`Camera/`)가 있어 Python 배포 경험이 있고, "엔진은 나중에 결정"과 "다른 서버에서 돌 수도 있음"이라는 두 요구가 모두 서비스 분리를 가리킨다. VMS 쪽 C++에는 `AnalyzerClient`(HTTP) 하나만 두고, 계약은 concept 문서 7절로 고정한다. 나중에 성능이나 배포 단순화가 필요하면 그때 C++로 옮겨도 계약이 같으니 UI와 저장 계층은 손대지 않는다.

## 13. 평가 방법

프로토타입 단계에서 다음 두 가지를 **먼저** 만든다. 모델과 프롬프트 선택은 이 수치로 한다.

1. **속성 정확도 셋**: 실제 설치 환경에서 200~300 프레임을 뽑아 사람이 라벨링(객체 종류, 상의 색, 행동, 조명). 모델별·프롬프트별로 필드 단위 정확도와 `unknown` 비율을 측정한다.
2. **검색 품질 셋**: 사용자가 실제로 할 법한 질의 50개와 정답 구간을 만든다. Recall@10, MRR, 첫 결과까지의 시간을 측정한다. 재검증 on/off 비교.
3. **처리량 측정**: 실제 GPU에서 이미지당 지연(p50, p95), 동시 요청 수에 따른 처리량, VRAM 사용량. 4.3절 표를 실측값으로 교체한다.

## 14. 단계별 로드맵

| 단계 | 목표 | 산출물 | 완료 기준 |
|------|------|--------|-----------|
| **0. 기반 안정화** | 리뷰 결함 수정, 상시 세션, remux 녹화, 타임스탬프 재생 | 안정적인 16채널 녹화·재생 VMS | 16채널 72시간 무중단, 임의 시각 재생 |
| **1. 분석 파이프라인** | 캡처 → Analyzer(Ollama+Gemma) → JSON 저장 | CaptureScheduler, AnalysisQueue, MetadataStore, Analyzer v1 | 30초 간격 16채널 지연 누적 없음, 평가셋 정확도 측정 |
| **2. 검색** | 질의 해석, 하이브리드 검색, 이벤트 그룹, AI Search 탭, 클릭 재생 | SearchEngine, UI | 검색 품질 셋 Recall@10 ≥ 0.7, 응답 2초 |
| **3. 품질·효율** | 변화 감지 게이팅, VLM 재검증, 채널 요약, 대시보드 | | 분석 예산 50% 절감, 재검증 정밀도 향상 확인 |
| **4. 확장** | 규칙 알람, 다중 프레임 행동 분석, 원격 Analyzer 다중화, 재처리 도구 | | |

단계 0과 1은 병렬 가능하다. Analyzer 서비스와 평가셋은 VMS 코드와 독립적으로 먼저 만들 수 있고, 그동안 VMS 쪽은 녹화를 붙인다.

## 15. 의견 정리

- **가장 먼저 할 일은 평가셋과 Analyzer 프로토타입이다.** 실제 카메라 프레임 200장을 Ollama + Gemma에 넣어 보고, 우리가 원하는 속성이 어느 정도 정확도로 나오는지 숫자로 확인해야 나머지 설계(간격, 모델 크기, 하드웨어)가 정해진다. 이건 반나절이면 된다.
- **"주기 캡처"를 "게이팅된 주기 캡처"로 처음부터 설계**하는 것이 좋다. 처리량 표에서 보듯 전수 분석은 예산의 대부분을 정적 장면에 쓴다.
- **검색 UI에서 해석 결과를 보여주는 것**이 신뢰의 핵심이다. 결과가 이상할 때 사용자가 "시스템이 '어제'를 어떻게 이해했는지" 볼 수 있어야 한다.
- **기존 VMS 결함을 먼저 고치지 않고 AI 기능을 얹으면** 상시 세션에서 문제가 증폭된다. known‑issues의 1~3번은 단계 0의 첫 작업이어야 한다.
- 제품 이름의 "지능형"은 결국 **검색 정밀도와 응답 속도**로 판단된다. 모델 크기 경쟁보다 스키마·프롬프트·게이팅·하이브리드 검색 같은 시스템 설계가 체감 품질을 더 크게 좌우한다.
